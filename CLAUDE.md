# RemoteVI: notes for Claude sessions

RemoteVI publishes a LabVIEW front panel (or any window) to a browser. It is pure G plus a web client: capture is BitBlt of the window's DWM surface, sent as PNG dirty rects over a WebSocket, and input goes back as posted Win32 messages.

Start with README.md, then docs/architecture.md, docs/protocol.md, docs/testing.md and docs/security.md.

## User preferences (binding)
- **Commits:** small, focused commits, one logical step each. Push without asking.
- **Save version 20.0:** every VI, the libraries and the project stay saved for LabVIEW 2020, so older code can use RemoteVI; newer LabVIEW compiles them on load. Develop and test in any newer LabVIEW, then save for 2020 (Tooling, "Save version"). Check with `python tools/dev/lv_versions.py --expect 20.0` (CI runs it).
- **Host input:** never move or affect the host cursor or keyboard. No SendInput, SetCursorPos, keybd_event or mouse_event. AttachThreadInput is not shipped. The user accepted it as a guarded fallback, but the permission classifier blocked it, so they must allow it explicitly first.
- **Pure G:** no custom DLLs. Windows system DLLs go through the Call Library wrappers built by `scripts/Build Win32 Wrappers.vi`.
- **LabVIEW projects:** virtual folders only, never auto-populating folders. `RemoteVI.lvproj` is generated by `python scripts/gen-lvproj.py`, build specs included; rerun it after adding or removing VIs outside `source/`.
- **Test like the user uses it:** every change end to end on the demo `examples/RemoteVI Demo.vi`, which has dialogs, through the browser path. Keep LabVIEW in the BACKGROUND. Run the fixture suites too.
- **Naming:** the stand-alone app is "RemoteVI Server". Never use the word "agent" in names, UI or docs.
- **Screenshots:** no full-desktop screenshots, because private windows are visible. Captures of LabVIEW or app windows and the stream are fine.
- **LabVIEW crashes and dialogs:**
  - Never kill LabVIEW or anything the user runs. Starting LabVIEW when it is not running is fine.
  - Never post WM_CLOSE or experiments to LabVIEW-owned dialogs. That hung LabVIEW once.

## Tooling
- **G generation:** labview-mcp: the pylabview composer (writes LabVIEW 2025 VIs) and, on LabVIEW 2026, the gRPC backend (writes 2026 VIs). AIXML sources live in `tools/aixml/<folder>/` next to their VIs. Both write a newer version than 20.0: save the result for 2020 afterwards.
  - Server VIs carry TCP refnums. Build them with `<labview-mcp>\bin\pylabview\python.exe tools\aixml\compose.py <xml> <vi> [search dirs]` (it finds the newest installed labview-mcp; `LVMCP_BIN` overrides).
  - After a recompose, compare the connector pane with the old VI (`lvai_connector_pane`): the composer may pick another pattern (4833 instead of 4815) with the same conIdx, and every caller then reports "Bad linkage to subVI". Fix with pylv_apply `{"op":"conpane","pattern":4815}`.
  - Panes and splitters: `tools/aixml/pane_parts.py`.
- **Embedded client:** after editing `web/index.html` run `node scripts/gen-index-html-vi.mjs --compose`. `tools/check-server.mjs` flags a stale embedded client.
- **Protocol reference:** `tools/lib/*.mjs` plus `tools/mock-server` (port 8090). Vectors are in `tests/vectors` (`npm run vectors`, `npm run vectors:check`). Keep them in sync with the G code.
- **Helper VIs and scripts:** in `tools/dev/` (see its README):
  - Launch Detached, Abort Path, FP Close Path, Mem, Notify Stop, Build Spec;
  - the library re-add chain: `mk_lists.py` → `Add To Library Files.vi` → `fixlib.py`;
  - `start-labview.ps1 [-Version 2020]`;
  - Save For Previous, `lv_versions.py`, `lvlib_version.py` (save version);
  - Remote Run, Remote Exec State (drive and check another LabVIEW over VI Server).
- **Save version:** after generating, recomposing or saving anything in a newer LabVIEW:
  1. `python tools/dev/lv_versions.py --expect 20.0` lists the VIs to convert; write their paths to a text file.
  2. Run `tools/dev/Save For Previous.vi` (items file, version 20.0) in the LabVIEW that has them in memory. It saves in place; close them without saving afterwards.
  3. `python tools/dev/lvlib_version.py source/RemoteVI.lvlib "hooks/RemoteVI Hooks.lvlib"` whenever LabVIEW saved a library (the library re-add chain does). `gen-lvproj.py` writes the project as 20.0.
  4. Check in LabVIEW 2020: start it with `tools/dev/start-labview.ps1` (VI Server port 3365, next to 2026 on 3364) and run `tools/dev/Remote Exec State.vi` from the newer LabVIEW over all VIs. Broken by design: the four IsX wrapper templates and `tests/fixtures/build/Fixture Tab Panel.vi`.
- **LabVIEW 2020 side by side:** the `LabVIEW.Application` ActiveX ProgID belongs to LabVIEW 2020 on this station and does not reach a running instance, so `tools/lv-share-url.ps1` fails. Drive 2020 with `tools/dev/Remote Run.vi` (Status.vi, result `text`; Launch Detached.vi, input `path`; Build Spec.vi). A build makes 2020 stop answering VI Server for a while: Run VI may return 1130 while the build still finishes - check the output files.

## Pitfalls that cost hours
- **Launching:** `lvai_run_vi_as_top_level` ABORTS long-running VIs at its timeout. Start servers detached with `tools/dev/Launch Detached.vi` (input `path`).
- **Library membership:** every recomposed VI loses it. Re-add it:
  1. Stop and close everything from RemoteVI: `Abort Path.vi` / `FP Close Path.vi`. `Mem.vi` with text "RemoteVI" must return nothing.
  2. `python tools/dev/mk_lists.py`.
  3. Run `tools/dev/Add To Library Files.vi` with inputs library path, items file and callers file (both in `tools/dev/`). Check that `add code max` = 0.
  4. `python tools/dev/fixlib.py`.
  5. Repeat until mk_lists reports 0 items. Errors 1562, 56002 and 56003 mean the library or a VI is still in memory.
- **Server Loop:** recomposing `Server/RemoteVI Server Loop.vi` loses reentrancy. Run `scripts/Set Reentrant.vi` on it, otherwise Start fails with 1096.
- **Window handles:** a panel's window handle changes on every launch. Never hard-code it.
- **Shares and tokens:**
  - Several shares per LabVIEW instance work, one port each: demo 8088, fixtures 8089, reference server 8090.
  - Every request needs the share's token (`?t=`). Get the links with `source/API/RemoteVI Status.vi` and pass `RVI_URL=<link>` to the suites (`tools/lv-share-url.ps1`).
  - Window targets also need `RVI_ORIGIN`: 0,46 with menu bar and toolbar, 0,20 with the menu bar only.
- **Builds:** the `lvai_build_from_build_specification` RPC is unimplemented on LabVIEW 2025. Release builds come from LabVIEW 2020 (2020 run-time engine; the hooks lvlibp must be built by the same version as the application that loads it). Build with `tools/dev/Build Spec.vi` (project, spec), which uses vi.lib/AppBuilder/BuildTargetBuildSpecification.vi. Output goes to `builds/` (git-ignored).
- **VI Server route:**
  - Built EXEs load only compiled code, so the hooks come from `builds/RemoteVI Hooks/RemoteVI Hooks.lvlibp`.
  - Cross-process tests: add `server.tcp.enabled=True` and `server.tcp.port=3370` to the fixture EXE's INI, then share its window with Start Window on 8090.
- **Known LabVIEW crashes:**
  - the composer's slide and knob parts;
  - Flush Queue;
  - panel property writes on VIs that are not open;
  - `{LV.Control} Replace` with NXG .ctl files;
  - remote `CvtPaneToPanelCoords`;
  - parallel MCP calls. Never run MCP calls in parallel.
- **AIXML probes:** sequence Close Reference through the error wire. An unwired Close Reference runs first and causes misleading error 66.
- **Git Bash heredocs:** they mangle backslash escapes such as `\3A` in AIXML. Write edit scripts with the Write tool.
- **LabVIEW 2020 compatibility:**
  - A library saved by a newer LabVIEW also carries that version in the header of its flattened icon (`NI.Lib.Icon`). LabVIEW 2020 then refuses the library (error 122) and every member VI is broken with "error of type 2000000". `lvlib_version.py` rewrites the header.
  - LabVIEW 2020's `LV Image to PNG Data.vi` has no compression input and writes uncompressed PNGs. RemoteVI calls LabVIEW's own `LVImageDataToPNGByteArray` instead (`Win32/LabVIEW LVImageDataToPNGByteArray.vi`, library `LabVIEW`, C calling convention), which takes the zlib level in every version.
  - A VI started over VI Server with Run VI has no open panel, and RemoteVI then streams a 0x0 frame. Start shared VIs through `Launch Detached.vi`, which opens the panel.
- **Fixture state:** relaunching a fixture that is still in memory keeps the last run's ring and tab values, while its log starts empty; the ring and tab tests then pick the current item and fail. Close the panel (`FP Close Path.vi`) before relaunching.
- **Tip strips:** LabVIEW shows its own tip strips only while it is the foreground application. RemoteVI therefore sends tip texts itself (`tips` message).
