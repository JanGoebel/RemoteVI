# RemoteVI architecture (v2)

RemoteVI shows a running VI's front panel in a web browser, pixel for pixel, and lets you operate it with mouse and keyboard. It replaces LabVIEW *Remote Panels* without the browser plug-in, the Run-Time Engine on the client, or the NI Web Server. You drop two VIs into your application, and the panel is reachable at `http://host:port/`.

## Design in one paragraph

The panel is a **picture going one way and raw input going the other**. The toolkit grabs the whole front panel window below its title bar - menu bar, toolbar, panel and scrollbars, exactly as the window shows them - with `PrintWindow`, sends only the parts that changed as PNGs over a WebSocket, and the browser draws them on a canvas. Mouse and keyboard events in the browser go back as Win32 window messages (`WM_LBUTTONDOWN`, `WM_MOUSEMOVE`, `WM_CHAR`, …), which the toolkit posts to the panel's native window with `PostMessageW`. LabVIEW then handles them exactly like local input. Nothing about the panel is modelled or re-implemented, so subpanels, splitters, tab controls, XControls, tables, graphs with cursors, custom controls, event structures and latched booleans all work as they do locally.

The first version (protocol v1, see git history) modelled each control through VI Server and wrote values with `Value (Signaling)`. That breaks down on real UIs: splitters, subpanel contents, scrolling, cursors and keyboard focus would each need their own adapter. v2 drops that model entirely.

## Constraints

| Constraint | Consequence |
|---|---|
| Pure G | No custom DLLs. Windows calls go through Call Library Function Nodes (`source/Win32`), one wrapper VI per function, generated by `scripts/Build Win32 Wrappers.vi` with VI scripting. A spec can ask for a node that runs in LabVIEW's UI thread (used for `GetKeyboardState`/`SetKeyboardState`). |
| No NI Web Server | HTTP request parsing and the WebSocket upgrade use **IG HTTP Server / IG HTTP Utils / IG WebSocket Stream** (VIPM, Illuminated G). WebSocket framing after the upgrade is our own (`source/Protocol`), because it's small and keeps the server a single loop. |
| Embeddable | The browser client is one self-contained file, `web/index.html`, embedded as a string constant, so a built EXE needs no support files. |
| LabVIEW 2025 | The code is generated with labview-mcp on LabVIEW 2025. |
| Windows | Input injection is Win32. Capture and streaming are platform-neutral. |

## Data flow

```
 ┌─────────── LabVIEW (IDE or EXE) ────────────────────────────────────────┐
 │  Your VI  ── RemoteVI Start.vi (This VI, port) ──► Server Loop (async)  │
 │                                                                         │
 │  Server Loop.vi (one loop, no event structure)                          │
 │   ├ TCP Wait On Listener (5 ms) → Accept Clients.vi: pending list       │
 │   │    per pending connection: TCP Read (immediate, timeout 0)          │
 │   │    head complete → Handle Connection.vi: GET / → index.html         │
 │   │                                       → GET /ws → IG upgrade → client │
 │   │    no complete head within 5 s, or peer gone → close                │
 │   ├ per client: TCP Read (immediate) → WS Decode Client Frame           │
 │   │    → Parse Input → ack | close (SC_CLOSE to a listed window)        │
 │   │      | Route Input (panel or other window) → Post Input             │
 │   │        (ScreenToClient + PostMessageW)                              │
 │   ├ Track Windows: dialogs, file dialogs, subVI panels (Win32 only)     │
 │   ├ Send Origin: `origin x y` to every client when it changed           │
 │   ├ Read Tips (after a geometry refresh) → Send Tips: `tips [...]`        │
 │   └ every 1/fps (16 ms right after a click/key), if any client:         │
 │        Capture Frame (GetDC + BitBlt of the client area)                │
 │        per client with < 2 frames in flight:                            │
 │          Dirty Rects(prev, cur) → Encode Rect PNG × n                   │
 │          → Frame Encode → WS Encode Server Frame → TCP Write            │
 │        Send Windows: `windows [...]` when it changed, then one          │
 │          WINDOW FRAME per window (same diff, flow control, seq)         │
 └─────────────────────────────────────────────────────────────────────────┘
                 ws://host:port/ws  (PNG frames ↓, input text ↑)
                         ┌──────────────────────────┐
                         │ Browser: web/index.html  │
                         └──────────────────────────┘
```

### Capture

* **The frame is the window below its title bar**: the client area of the front panel window, which holds LabVIEW's menu bar (LabVIEW draws it itself, also a custom run-time menu bar - measured on LabVIEW 2025: `GetMenu` returns NULL and `GetMenuBarInfo` fails, so there is no native menu bar to add above it), the toolbar, the panel and its scrollbars. `RemoteVI Capture Frame.vi` copies the client area from the window's composited surface: `GetDC` of the window and `BitBlt` into a memory bitmap, then `GetDIBits` (`RemoteVI Copy Window.vi`). With desktop composition every top-level window draws into its own surface, so this sees the window's pixels while it is covered by other windows (measured with the panel behind a maximised window, pixel-identical), and it does not make the window draw itself again. Until this change the server drew the window with `PrintWindow` (`WM_PRINT`), which made LabVIEW repaint the whole window for every frame: 40-50 ms of LabVIEW's UI thread per capture on the demo, graph included, so at 20 fps the UI thread was busy almost all the time and posted input waited for it; the copy takes 2-5 ms. No VI Server call, so the same capture serves every frame, also while a popup's modal loop holds LabVIEW's UI thread. (`FP.Get Image` shows no menu bar, toolbar or scrollbars and blocks while a popup is open; `RemoteVI Capture Panel.vi` stays for the benchmarks.) A window that cannot be drawn (minimized, gone) keeps the last frame.
* **Origin:** the panel area starts at `Front Panel Window:Panel Bounds` minus the frame origin, below the menu bar and toolbar (46 px on the fixture). `RemoteVI Get Panel Geometry.vi` reads it with the window geometry (before the loop, then every 500 ms while no popup is open); a new client gets `origin x y` with its greeting (`RemoteVI Origin Message.vi`), and `RemoteVI Send Origin.vi` tells every client when it changes (docs/protocol.md §3.3). All protocol coordinates are frame coordinates.
* Pixels: 2D U32 `[row, column]`, `0x00RRGGBB` (GetDIBits, 32-bit top-down).
* **Dirty Rects**: a 64 × 64 tile grid. The dirty tiles of each tile row merge into one band. Tiles are compared with `Array Subset` + `Equal?` element by element + `And Array Elements` (`RemoteVI Dirty Band.vi`); an unchanged band costs one comparison.
* **Encode Rect PNG**: `Array Subset` → `Flatten Pixmap` → NI's `LV Image to PNG Data.vi` with compression on. The default (no compression) gives 1.7 MB for a full panel, so compression matters.
* Each client keeps the last pixmap it was sent, plus `seq`/`acked` for flow control (at most 2 frames in flight).

### Input

* The browser sends Win32 message numbers and `wParam`, with frame-pixel coordinates for mouse messages (docs/protocol.md §4).
* Server: screen point = frame origin + (x, y) - the frame origin is the client-area origin, `geo.panelX/panelY` (the field name is historical). `ScreenToClient(hWnd)` converts it. Then `PostMessageW(hWnd, msg, wParam, lParam)`. `WM_MOUSEWHEEL` takes screen coordinates.
* **Menu bar, toolbar, scrollbars** are in the client area, so their input is ordinary client-area input (measured on LabVIEW 2025): a click on a menu bar title opens its menu, an `LVMenuWnd` that is driven like every other menu (Popups); a click on a toolbar button (Abort, Pause in run mode) works as locally; a click on a scrollbar arrow or a drag of its thumb scrolls the panel (the drag follows the capture rule below).
* `hWnd` = `Front Panel Window:OS Window` (an I32, widened through I64 to U64).
* Only the messages in protocol §4.3 are posted.
* **One message at a time:** after each post the server waits until LabVIEW has handled it (two `WM_NULL` sent to the panel, `RemoteVI Wait Input Handled.vi`). Burst-posted key messages are dropped and reordered by LabVIEW (measured), and the next rule needs the result of the previous message. The exception is a hover move (`WM_MOUSEMOVE` with no button held): nothing depends on it having been handled, and at up to 60 moves per second the round trips kept the server loop waiting on LabVIEW's busy UI thread (`RemoteVI Post Input.vi`).
* **Frames right after input:** for 300 ms after a client posted a click or a key the server loop makes a frame every 16 ms instead of every 1000/fps ms, so the change the input causes reaches the browser at once instead of up to a frame period later. Measured with `tools/perf.mjs` on the demo, LabVIEW in the background, a second browser connected: click-to-photon on the Enable switch median 93-185 ms before (PrintWindow, frames at the fps period), 59 ms after (p90 90); a typed character 53-204 ms before, 35 ms after; the rest is mostly LabVIEW's own UI thread, which handles a posted click 0-50 ms late while the demo redraws its graph (measured by posting a click and polling the window's surface).
* **Moves and button-ups in screen or client coordinates** depending on whether LabVIEW's UI thread holds the mouse capture right now (`GetGUIThreadInfo`, `RemoteVI Mouse Captured.vi`): LabVIEW reads screen coordinates while it tracks a press (buttons, sliders, text selection), client coordinates otherwise (a switch-when-pressed lost its button-up in screen coordinates and stayed "held").
* **Modifier keys:** LabVIEW reads Shift/Ctrl/Alt with `GetKeyState`, which posted messages do not update. The server tracks what the remote user holds (`RemoteVI Track Modifiers.vi`) and, when it changes and no popup is open, writes it into the key state of LabVIEW's UI thread with `GetKeyboardState`/`SetKeyboardState` wrappers configured to run in the UI thread (`RemoteVI Set Modifier Keys.vi`, `RemoteVI Apply Modifiers.vi`). Nothing outside that thread changes; the host keyboard and cursor are never touched (no `SendInput`, `keybd_event`, `mouse_event` or `SetCursorPos`).
* A mouse-path click on a popup (one that takes no keys, see Popups) is posted no sooner than 350 ms after the popup appeared: LabVIEW ignores clicks on a freshly opened ring menu (measured: about 250 ms). Menus are driven with keys, which need no delay.
* Printable characters go as `WM_CHAR`, so the host keyboard layout doesn't matter. Other keys get their scan code in `lParam` when the client sent none (LabVIEW lost the arrow of a scan-code-less Shift+Right, measured).
* A double click arrives as `WM_LBUTTONDBLCLK` and is posted as a second `WM_LBUTTONDOWN`: LabVIEW's panel window class has no `CS_DBLCLKS`, so LabVIEW detects double clicks from two downs and ignores a posted DBLCLK (measured with a listbox Double Click event).
* `WM_MOUSEWHEEL` with screen coordinates reaches the control under the posted point (measured: a numeric's Mouse Wheel event, positive delta for "away from the user").

### Popups (menus, dropdowns, graph palette, tip strips)

Ring and enum menus, right-click menus, combo-box lists and graph-palette popups are separate top-level windows (`LVMenuWnd` and others) owned by LabVIEW. They are not part of the panel window's own picture. While one is open, LabVIEW's UI thread runs a modal loop, and every VI Server UI call blocks until it closes. So the server watches for popups with Win32 calls only (`RemoteVI Find Popups.vi`) on every loop iteration, and while one is open it makes no VI Server UI calls. A short hold-off after each remote click also prevents capturing just as a menu opens.

**Walking only LabVIEW's part of the Z order:** `RemoteVI Find Popups.vi` and `RemoteVI List Windows.vi` walk the top-level windows with `FindWindowExW(0, previous, NULL, NULL)` from the top down, and stop at the panel's owner (`GetWindow(GW_OWNER)`, LabVIEW's hidden frame window `LVFrame`). LabVIEW's popups, its dialogs, the native file dialogs and the front panels are all owned by `LVFrame`, and an owned window always lies above its owner, so nothing of interest lies below it (a panel without an owner is walked to the end). Walking all ~860 top-level windows of a busy desktop took 61 ms (Find Popups, every iteration) and 126 ms (List Windows, every 200 ms); the demo's frame gaps were median 136 ms, p90 675 ms. With the walk ending at `LVFrame` it takes a few ms: median 80 ms, p90 97 ms (measured).

* **Picture:** each popup is captured with `PrintWindow` (`RemoteVI Capture Window.vi`, flags 0: the window paints itself through `WM_PRINT`). That works whether the popup is visible, covered or on another monitor, and also for the panel while a menu's modal loop runs. `PW_RENDERFULLCONTENT` gave the same pixels for the panel, LabVIEW's menus, the colour picker and the line width popup, but took 35 instead of 16 ms for an 837 × 586 panel and 38 instead of 5 ms for the plot legend menu (measured), so it is no longer used. The capture goes to the browser as an OVERLAY message at the popup's position relative to the panel, unclipped, so menus that extend past the panel are shown in full.
* **Invisible on the host:** popups that appear within 1 s of a remote click, or while a popup hidden this way is still open (a submenu the remote hover opened), are made layered with alpha 0 (`RemoteVI Hide Window.vi`). They keep working. Popups opened at the host stay visible and are streamed as well. To hide a menu before it shows, the popups are listed a second time in the iteration that posted the click or key, right after the posting (`RemoteVI Retrack Popups.vi`, also while a popup is open, for submenus the hover opened); when the listing changed it lists again every 25 ms (at most 6 times) until two listings agree, because before some menus LabVIEW shows a short-lived window of another size for 30-80 ms, which must not reach the OVERLAY. The OVERLAY of a changed listing goes out before that iteration's frame. LabVIEW fades a new menu in (alpha 0 to 255 over about 170 ms), which undoes alpha 0 until the next iteration hides it again. An empty window region (`SetWindowRgn`) kept such a menu fully invisible (0-27 ms on the host), but with it the menus could no longer be driven with keys (LV tests 16, 17, 18 and 20 failed), so it is not used. Measured on the fixture, 5 openings each (ring menu / shortcut menu): visible on the host 121 / 72 ms (median), first OVERLAY 337 / 160 ms; before the second listing 400-1000 ms and 479-859 ms.
* **Nothing is moved for a menu - keys instead of the mouse.** LabVIEW hit-tests popup clicks with the real cursor position (`GetCursorPos`) against the popup window's real position and ignores posted coordinates (measured). The host cursor is never moved. The previous design moved the invisible popups under the host cursor instead; a submenu that opened from a moved parent was then placed by LabVIEW relative to the moved parent and the monitor the host cursor was on - near a monitor edge on the other side - so the overlay showed it on top of its parent and clicks landed off target. Now LabVIEW menus are driven with keys posted to the panel window, which holds the mouse capture while a menu is open (measured on LabVIEW 2025: `VK_DOWN`/`VK_UP` move the highlight by one item, skipping separators; `VK_RETURN` chooses the highlighted item or opens its submenu; `VK_RIGHT` opens the highlighted item's submenu and does nothing on an item without one; `VK_LEFT` closes the deepest submenu; the plot legend menu wraps around at its ends, a ring menu does not). Every menu therefore stays where LabVIEW put it, a submenu opens beside its unmoved parent exactly as locally, and the overlay positions are the real ones.
  * **Where the pointer is:** the menus are listed fresh, top-most (deepest) first, with `FindWindowExW(…, "LVMenuWnd", …)` (`RemoteVI List Menus.vi`, under 0.1 ms), and the one under the pointer is found.
  * **Moving the highlight onto a row** (`RemoteVI Highlight Menu Row.vi`): the menu is captured and its middle column searched for the Windows highlight colour (`GetSysColor(COLOR_HIGHLIGHT)`, `RemoteVI Menu Highlight.vi`) - LabVIEW paints the selected item in it across the whole row. One `VK_DOWN`/`VK_UP` is posted towards the pointer's row, the menu captured again until the highlight moved (`RemoteVI Wait Highlight Change.vi`, at most 120 ms: captured right after the `WM_NULL` round trip, the old highlight was still seen), and so on until the highlighted band contains the row. It stops without a hit when the band does not move (end of a non-wrapping menu, nothing selectable), jumps past the row (separator, disabled item) or wraps (undone with one key the other way). A menu nothing is highlighted in yet gets one probe key first - but only a window with the menu background colour (`COLOR_MENU`): a key posted into the colour picker spoils its next click (measured), and the picker's background is 0xF7F7F7.
  * **Hover** (`RemoteVI Note Popup Pointer.vi` stores each `WM_MOUSEMOVE` a client sends while a popup is open in `RemoteVI Menu Pointer.vi`, a functional global; `RemoteVI Menu Hover.vi` applies the latest position once per server loop iteration, so a burst of moves costs one navigation): over the deepest menu the highlight follows the pointer; after 400 ms on one item `VK_RIGHT` is posted once - only when the item shows a submenu arrow (`RemoteVI Menu Highlight.vi` submenu?: a pixel that is not the highlight colour in the strip at the right end of the band), because in a menu of the panel's menu bar `VK_RIGHT` on an item without a submenu switches to the next menu bar menu (measured) - which opens its submenu like a local hover. Over a parent of open submenus nothing happens on the item that opened the submenu; on another item, once the pointer has rested there 300 ms (so crossing the parent on the way into the submenu does not close it), the submenus are closed with `VK_LEFT` and the parent's highlight follows.
  * **Click** (`RemoteVI Menu Click.vi`): a button-down on a menu row closes the submenus above that menu with `VK_LEFT` (nothing happens on the item that opened the open submenu, as locally), moves the highlight onto the row and posts `VK_RETURN`, which chooses the item or opens its submenu (measured: `VK_RETURN` opens a submenu like `VK_RIGHT`, so no wait for a popup that may or may not appear is needed). A click on a separator or disabled item chooses nothing. The button-up of a click turned into keys is dropped (`RemoteVI Swallow Button Up.vi`), and so is the button-up that released the click which opened the menu.
* **Popups that take no keys - the mouse path** (`RemoteVI Plain Popup Click.vi`): the colour picker and the line width popup of a plot legend are `LVMenuWnd` windows too but show no highlight and ignore the arrow keys; popups of other classes (graph palette popups and the like) go the same way. For a button message on such a window only that window is moved, by d = real cursor - clicked point taken from its actual position, a `WM_MOUSEMOVE` and the message are posted with the cursor position in `lParam` (`RemoteVI Post At Cursor.vi`), and if the window is still open it is moved back to where LabVIEW put it. The down and the up are each moved and moved back (measured: the line width and the colour are chosen). Between messages every window is at its natural place, so a moved window can never misplace another popup or the overlay. While such a popup is open, its parent menus take no keys either (`VK_LEFT` does not close the colour picker, measured), so the hover does nothing on them and a click on them goes through the mouse path, which closes the whole menu as LabVIEW does. A mouse-path click is posted no sooner than 350 ms after the popup appeared (`RemoteVI Wait Popup Age.vi`): LabVIEW ignores clicks on a freshly opened ring menu (measured: about 250 ms). Keys need no such delay (measured: `VK_DOWN` 70 ms after the plot legend menu appeared).
* **Click outside:** a click whose point lies outside every popup is not posted. The button-down sends `WM_CANCELMODE` to the panel with `SendMessageTimeoutW`, which closes every open LabVIEW popup; the button-up is dropped.
* **Tip strips** (`LVTipStrip`) are not part of the OVERLAY and do not switch input into popup mode. LabVIEW shows them for posted hover (no real cursor dwell needed) and hides them on the next posted move off the control, but only while LabVIEW is the active (foreground) application (measured: with another program in front no tip strip appears, for posted and remote hover alike) - and a remotely operated machine usually has another program in front. So the server sends the texts instead: right after each geometry refresh (every 500 ms, never while a popup or modal window is open) `RemoteVI Read Tips.vi` reads `Visible`, `Tip Strip`, `Position` and `Bounds` of the panel's controls (top level; controls inside tab pages and clusters are not read) and `RemoteVI Tips Message.vi` builds `tips [...]` with the bounds in frame coordinates; a new client gets it with its greeting, all clients again when it changed (`RemoteVI Send Tips.vi`, docs/protocol.md §3.3). The browser shows the text after a 500 ms hover, styled like a LabVIEW tip strip. A LabVIEW tip strip that appears while the host cursor is outside the panel window can only stem from the remote pointer and is still hidden on the host (layered, alpha 0); with the host cursor over the panel it may be the host user's own and stays visible.
* **Panel keeps updating:** LabVIEW keeps redrawing the panel while a menu's modal loop runs (measured: two `PrintWindow` captures 300 ms apart differ in the graph), and the frame is always drawn by `PrintWindow`, so frames keep coming while a popup is open. (Before the whole window was streamed, frames came from `FP.Get Image`, which blocks in the modal loop, and a popup switched to `PrintWindow` pasted over the last `FP.Get Image` capture.)
* **No stall when a popup opens:** nothing in the popup path waits for a popup any more (the old path waited until the popup was 350 ms old, then up to 300 ms for the popups to change, then pressed `VK_RIGHT` and waited again - about 1 s without a frame for a click whose button-up landed on the new menu, measured). The overlay is captured and encoded in an iteration without a frame, or at the latest 150 ms after the last overlay check even in a frame iteration: since window tracking made the loop slower, almost every iteration made a frame and the overlay was starved (menus opened on the host but never reached the browser). Measured on the demo with a client acking every frame (20 fps, median gap 57 ms): opening the plot legend menu, the Mode ring and a shortcut menu gave frame gaps of 1013-1026 ms before, 100-180 ms after (12 of 15 openings at or under 150 ms); the machine's gaps without any popup reach 160 ms.
* **Minimized panel:** LabVIEW ignores input to it. The server restores it with `ShowWindow(SW_SHOWNOACTIVATE)`, without taking focus.

### Other windows: dialogs, native file dialogs, subVI panels

The application's other windows (docs/protocol.md section 7) are tracked with Win32 calls only, like the popups: while a dialog is up LabVIEW's UI thread runs the dialog's modal loop, and every VI Server UI call blocks until it closes (measured on LabVIEW 2025: an ActiveX call into LabVIEW does not return while a Two Button Dialog is open).

* **Listing** (`RemoteVI List Windows.vi`, called by `RemoteVI Track Windows.vi` at most every 200 ms while a client is connected; it walks the Z order down to `LVFrame` only, see Popups): LabVIEW's visible top-level windows other than the panel, not popups (`RemoteVI Window Popup Info.vi`), with a size (LabVIEW's hidden frame window `LVFrame` is 0 x 0). Of those it lists native dialogs (`#32770`), windows owned by the panel or by another listed window (`GetWindow` `GW_OWNER`, up to 8 steps), windows listed before, and windows that appeared while the panel is disabled (`IsWindowEnabled` FALSE). Measured on LabVIEW 2025: a Two Button Dialog is an `LVDChild` without a caption, owned by `LVFrame`, not by the panel, and LabVIEW disables all its windows while it is up; the File Dialog function shows a native `#32770` window, also owned by `LVFrame`. "Appeared" compares with a baseline: while the panel is enabled the baseline is the candidate set of the previous listing, so a dialog that becomes visible just before LabVIEW disables the panel still counts; while the panel is disabled the baseline is kept. IDE windows that were there before (Project Explorer, block diagrams, other VIs) are therefore not listed.
* **Description** (`RemoteVI Window Info.vi`): id = HWND, caption with `GetWindowTextW` as UTF-16 and written as an ASCII-only JSON string literal (`RemoteVI JSON String.vi`, `\uXXXX` escapes) so the text message is valid UTF-8 whatever the host's code page; a window without a caption gets its owner's (`LabVIEW` for LabVIEW's own dialogs). Client rect (`RemoteVI Frame Rect.vi`) relative to the main frame's origin, `modal` = panel disabled, `active` = `hwndActive` of the UI thread (`RemoteVI Thread Windows.vi`, `GetGUIThreadInfo`), `closable` = `WS_SYSMENU`.
* **Sending** (`RemoteVI Send Windows.vi`): each client gets `windows [...]` (`RemoteVI Windows Message.vi`, the JSON written field by field) whenever it differs from what that client was told - on connect too, as its last list starts empty. In an iteration that made a frame each listed window is drawn with `PrintWindow` and cut to its client area (`RemoteVI Capture Windows.vi`, the same `RemoteVI Capture Frame.vi` as the panel - measured pixel-exact for the Two Button Dialog against an independent `PrintWindow` of its client area, and complete for the native file dialog with flags 0) and goes out as a WINDOW FRAME (`RemoteVI Window Frame Encode.vi`) with the dirty-rect path of FRAME, diffed against the picture of that window this client was last sent (`window frames` in the client cluster; a new window is sent whole) and under the same flow control, `seq` shared with FRAME (`RemoteVI Send Window Frame.vi`).
* **No VI Server while modal:** while a listed window is modal the server loop makes no VI Server call (geometry refresh, VI-stopped check), exactly as while a popup is open.
* **Input** (`RemoteVI Route Input.vi`, per message, before `RemoteVI Post Client Input.vi`): a mouse message goes to the front-most listed window whose client area holds the point, else to the panel; while a popup is open, to the window the client last pressed a button in (`key window` in the client cluster), whose popup it is. The geometry handed on keeps the frame origin (main-frame coordinates are screen offsets) and takes the window's client origin, so Translate Input/Post Input work unchanged - LabVIEW dialogs track presses like a panel (screen coordinates while captured). A native dialog consists of child windows: the point is followed down with `ChildWindowFromPointEx` to the deepest visible child, and the geometry is chosen so that every posted `lParam` is that child's client coordinates (a Windows button wants its button-up in client coordinates even while it holds the capture; measured: Cancel of the file dialog clicked remotely). Keys go to the front-most modal window, else to `key window` while it is listed, else to the panel - inside the window to its focus child (`hwndFocus` whose `GetAncestor(GA_ROOT)` is the window: the file name box of the file dialog, where a posted Escape cancels, measured). While a modal window is listed a mouse message for the panel is dropped: LabVIEW would handle a message posted to its disabled panel. `x <id>` posts `WM_SYSCOMMAND` `SC_CLOSE` - what the title bar's close button sends - to a listed window with a close box only (`RemoteVI Close Window.vi`); a bare `WM_CLOSE` destroyed a Two Button Dialog's window while the dialog function kept waiting, which hung the calling VI and LabVIEW's VI Server (measured).

### Start and Stop

`RemoteVI Start.vi` reports a server that cannot serve. One Server Loop per LabVIEW application instance (it is not reentrant): when it is already running, Start launches nothing and returns error 5001. Otherwise it launches the loop and waits until the loop has created its TCP listener - the loop sends the listener's error cluster on the notifier `RemoteVI:<port>:started` - and returns that error (60 when the port is in use; the loop has then already ended), or 5002 when nothing arrives within 2 s. Before this, both cases returned without an error and nothing listened (measured with the previous Start.vi: port held by another process, error out clean).

### HTTP

* `GET /` → `index.html` (embedded constant) with the security headers.
* `GET /ws` with a valid upgrade and same-origin `Origin` → IG `Prepare WebSocket Upgrade Response` → `Write Response to TCP`. From then on, the raw TCP connection carries our WebSocket frames.
* Anything else → `404`. One request per connection.

`source/RemoteVI.lvlib` owns every VI under `source/`. Its virtual folders (API, Server, Capture, Protocol, Input, Win32) mirror the disk folders; no file was moved, and the VIs' qualified names are `RemoteVI.lvlib:<VI name>`. Every member is public on purpose: the check VIs in `tests/caraya/support`, the fixture, the examples and the spikes call internal VIs directly. The entry points are `API/RemoteVI Start.vi` and `API/RemoteVI Stop.vi` (the library description says so); everything else may change. Start opens `Server/RemoteVI Server Loop.vi` by path through VI Server, which works for a library member unchanged. In `RemoteVI.lvproj` the library appears inside the auto-populating `source` folder; it has no entry of its own.

Regenerating a member - composing it from `tools/aixml/` or rebuilding a Win32 wrapper with `scripts/Build Win32 Wrappers.vi` - writes a VI that belongs to no library. Add it back through LabVIEW (Project Explorer, or `{LV.ProjectItem} AddItem` on the library) with its callers loaded, so they relink to the qualified name, and save the callers.

Every pure VI (Protocol, Dirty Rects) has a JS reference function and shared vectors in `tests/vectors/`.
