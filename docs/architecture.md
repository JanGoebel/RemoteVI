# RemoteVI architecture (v2)

RemoteVI shows a running VI's front panel in a web browser, pixel for pixel, and lets you operate it with mouse and keyboard. It replaces LabVIEW *Remote Panels* without the browser plug-in, the Run-Time Engine on the client, or the NI Web Server. You drop two VIs into your application, and the panel is reachable at `http://host:port/`.

## Design in one paragraph

The panel is a **picture going one way and raw input going the other**. The toolkit grabs the panel with `FP.Get Image`, sends only the parts that changed as PNGs over a WebSocket, and the browser draws them on a canvas. Mouse and keyboard events in the browser go back as Win32 window messages (`WM_LBUTTONDOWN`, `WM_MOUSEMOVE`, `WM_CHAR`, …), which the toolkit posts to the panel's native window with `PostMessageW`. LabVIEW then handles them exactly like local input. Nothing about the panel is modelled or re-implemented, so subpanels, splitters, tab controls, XControls, tables, graphs with cursors, custom controls, event structures and latched booleans all work as they do locally.

The first version (protocol v1, see git history) modelled each control through VI Server and wrote values with `Value (Signaling)`. That breaks down on real UIs: splitters, subpanel contents, scrolling, cursors and keyboard focus would each need their own adapter. v2 drops that model entirely.

## Constraints

| Constraint | Consequence |
|---|---|
| Pure G | No custom DLLs. Windows calls go through Call Library Function Nodes (`source/Win32`), one wrapper VI per function, generated by `scripts/Build Win32 Wrappers.vi` with VI scripting. A spec can ask for a node that runs in LabVIEW's UI thread (used for `GetKeyboardState`/`SetKeyboardState`). |
| No NI Web Server | HTTP request parsing and the WebSocket upgrade use **IG HTTP Server / IG HTTP Utils / IG WebSocket Stream** (VIPM, Illuminated G). WebSocket framing after the upgrade is our own (`source/Protocol`), because it's small and keeps the server a single loop. |
| Embeddable | The browser client is one self-contained file, `web/index.html`, embedded as a string constant, so a built EXE needs no support files. |
| LabVIEW 2025 | The code is generated with labview-mcp on LabVIEW 2025. |
| Windows | Input injection is Win32. Capture and streaming are platform-neutral. |

## Data flow

```
 ┌─────────── LabVIEW (IDE or EXE) ────────────────────────────────────────┐
 │  Your VI  ── RemoteVI Start.vi (This VI, port) ──► Server Loop (async)  │
 │                                                                         │
 │  Server Loop.vi (one loop, no event structure)                          │
 │   ├ TCP Wait On Listener (5 ms) → Accept Clients.vi: pending list       │
 │   │    per pending connection: TCP Read (immediate, timeout 0)          │
 │   │    head complete → Handle Connection.vi: GET / → index.html         │
 │   │                                       → GET /ws → IG upgrade → client │
 │   │    no complete head within 5 s, or peer gone → close                │
 │   ├ per client: TCP Read (immediate) → WS Decode Client Frame           │
 │   │    → Parse Input → ack | Post Input (ScreenToClient + PostMessageW) │
 │   └ every 1/fps, if any client:                                         │
 │        Capture Panel (FP.Get Image → Unflatten Pixmap)                  │
 │        per client with < 2 frames in flight:                            │
 │          Dirty Rects(prev, cur) → Encode Rect PNG × n                   │
 │          → Frame Encode → WS Encode Server Frame → TCP Write            │
 └─────────────────────────────────────────────────────────────────────────┘
                 ws://host:port/ws  (PNG frames ↓, input text ↑)
                         ┌──────────────────────────┐
                         │ Browser: web/index.html  │
                         └──────────────────────────┘
```

### Capture

* `FP.Get Image` with *visible area only*, 24-bit. Spike result: 10–45 ms for a 950 × 620 panel. It runs in the UI thread, so the server loop captures only while clients are connected, at most at the configured fps.
* `Unflatten Pixmap` → 2D U32 `[row, column]`, `0x00RRGGBB`.
* **Dirty Rects**: a 64 × 64 tile grid. The dirty tiles of each tile row merge into one band. Tiles are compared with `Array Subset` + `Equal?` element by element + `And Array Elements` (`RemoteVI Dirty Band.vi`); an unchanged band costs one comparison.
* **Encode Rect PNG**: `Array Subset` → `Flatten Pixmap` → NI's `LV Image to PNG Data.vi` with compression on. The default (no compression) gives 1.7 MB for a full panel, so compression matters.
* Each client keeps the last pixmap it was sent, plus `seq`/`acked` for flow control (at most 2 frames in flight).

### Input

* The browser sends Win32 message numbers and `wParam`, with panel-pixel coordinates for mouse messages (docs/protocol.md §4).
* Server: screen point = `Panel Bounds` top-left + (x, y). `ScreenToClient(hWnd)` converts it; it handles the toolbar, which is inside the client area in the IDE. Then `PostMessageW(hWnd, msg, wParam, lParam)`. `WM_MOUSEWHEEL` takes screen coordinates.
* `hWnd` = `Front Panel Window:OS Window` (an I32, widened through I64 to U64).
* Only the messages in protocol §4.3 are posted.
* **One message at a time:** after each post the server waits until LabVIEW has handled it (two `WM_NULL` sent to the panel, `RemoteVI Wait Input Handled.vi`). Burst-posted key messages are dropped and reordered by LabVIEW (measured), and the next rule needs the result of the previous message.
* **Moves and button-ups in screen or client coordinates** depending on whether LabVIEW's UI thread holds the mouse capture right now (`GetGUIThreadInfo`, `RemoteVI Mouse Captured.vi`): LabVIEW reads screen coordinates while it tracks a press (buttons, sliders, text selection), client coordinates otherwise (a switch-when-pressed lost its button-up in screen coordinates and stayed "held").
* **Modifier keys:** LabVIEW reads Shift/Ctrl/Alt with `GetKeyState`, which posted messages do not update. The server tracks what the remote user holds (`RemoteVI Track Modifiers.vi`) and, when it changes and no popup is open, writes it into the key state of LabVIEW's UI thread with `GetKeyboardState`/`SetKeyboardState` wrappers configured to run in the UI thread (`RemoteVI Set Modifier Keys.vi`, `RemoteVI Apply Modifiers.vi`). Nothing outside that thread changes; the host keyboard and cursor are never touched (no `SendInput`, `keybd_event`, `mouse_event` or `SetCursorPos`).
* A click on a popup is posted no sooner than 350 ms after the popup appeared: LabVIEW ignores clicks on a freshly opened ring menu (measured: about 250 ms).
* Printable characters go as `WM_CHAR`, so the host keyboard layout doesn't matter. Other keys get their scan code in `lParam` when the client sent none (LabVIEW lost the arrow of a scan-code-less Shift+Right, measured).
* A double click arrives as `WM_LBUTTONDBLCLK` and is posted as a second `WM_LBUTTONDOWN`: LabVIEW's panel window class has no `CS_DBLCLKS`, so LabVIEW detects double clicks from two downs and ignores a posted DBLCLK (measured with a listbox Double Click event).
* `WM_MOUSEWHEEL` with screen coordinates reaches the control under the posted point (measured: a numeric's Mouse Wheel event, positive delta for "away from the user").

### Popups (menus, dropdowns, graph palette, tip strips)

Ring and enum menus, right-click menus, combo-box lists and graph-palette popups are separate top-level windows (`LVMenuWnd` and others) owned by LabVIEW. They are not part of `FP.Get Image`. While one is open, LabVIEW's UI thread runs a modal loop, and every VI Server UI call blocks until it closes. So the server watches for popups with Win32 calls only (`RemoteVI Find Popups.vi`) on every loop iteration, and while one is open it makes no VI Server UI calls. A short hold-off after each remote click also prevents capturing just as a menu opens.

* **Picture:** each popup is captured with `PrintWindow` (`RemoteVI Capture Window.vi`). That works whether the popup is visible, covered or on another monitor. The capture goes to the browser as an OVERLAY message at the popup's logical position relative to the panel, unclipped, so menus that extend past the panel are shown in full.
* **Invisible on the host:** popups that appear within 1 s of a remote click are made layered with alpha 0 (`RemoteVI Hide Window.vi`). They keep working. Popups opened at the host stay visible and are streamed as well.
* **Clicks without moving the cursor:** LabVIEW hit-tests popup clicks with the real cursor position (`GetCursorPos`) against the popup window's real position. Posted coordinates, posted keys and `SendMessage` are all ignored (measured). So the server moves the invisible popup windows by `d = realCursor - clickedPoint`, which puts the clicked item under the host cursor, then posts the button message with the real cursor in `lParam`. It then waits until the popup set changes (at most 300 ms) before moving the popups again. New popups, such as a submenu, appear next to the displaced parent, so their logical position is `real - d`. `d` resets when the last popup closes. The host cursor never moves.
* **Click outside:** a click whose point lies outside every popup (logical rectangles) is not posted. The button-down sends `WM_CANCELMODE` to the panel with `SendMessageTimeoutW`, which closes every open LabVIEW popup; the button-up is dropped. A posted click outside closes a plain menu, but once a submenu is open LabVIEW ignores posted clicks and keys altogether, while a sent `WM_CANCELMODE` still closes the whole menu (measured).
* **Stale popup list:** a ring menu closes and reopens itself right after the posted button-down (measured), so the list the server loop saw can name a window that is already gone. Post Input checks the listed windows with `IsWindowVisible`; if one is gone it lists the popups again (`RemoteVI Find Popups.vi`, logical = real - d), for at most 100 ms.
* **No hover:** LabVIEW updates the highlight only on real cursor motion, so moves and wheel are dropped while a popup is open.
* **Submenus:** LabVIEW hit-tests a submenu against the place where it opened it. Once a submenu is open, posted clicks are ignored after the popups were moved - in the submenu and in its parent - while posted keys (`VK_LEFT`, `VK_RIGHT`, `VK_RETURN` to the panel window) still work; a submenu that LabVIEW opened at its final place takes a click (measured). So a button-down on a LabVIEW menu while a submenu is open first closes submenus with `VK_LEFT` (`RemoteVI Prepare Menu Click.vi`, `RemoteVI Post Menu Key.vi`): all of them for a click on the bottom-most menu, otherwise those above the clicked one and the clicked one itself. Only the menus still open are moved by `d`; a closed clicked submenu is reopened with `VK_RIGHT`, which LabVIEW places next to the moved parent with the clicked point under the host cursor; the click follows 350 ms later (a button-up about 10 ms after the reopen was ignored, measured). A click on an entry that opens a submenu only highlights it, so when the popups are unchanged 300 ms after a button-up on a menu, `VK_RIGHT` opens the highlighted entry's submenu (nothing happens on an entry without one, measured).
* **Tip strips** (`LVTipStrip`) are captured and sent in the OVERLAY like the popups, but they do not switch input into popup mode and do not stop VI Server calls: LabVIEW shows them for posted hover (no real cursor dwell needed) and hides them on the next posted move off the control (measured). A tip strip that appears while the host cursor is outside the panel window can only stem from the remote pointer and is hidden on the host (layered, alpha 0); with the host cursor over the panel it may be the host user's own and stays visible.
* **Panel keeps updating:** FP.Get Image would block in the menu's modal loop, but LabVIEW keeps redrawing the panel (measured: two `PrintWindow` captures 300 ms apart differ in the graph). While a popup is open, and for 300 ms after a click, each frame is the panel window drawn by `PrintWindow` (`RemoteVI Capture Window.vi` on the panel hWnd), cut at Panel Bounds and pasted over the last FP.Get Image capture. The right and bottom 17 px stay from that capture: there the window shows LabVIEW's scrollbars where FP.Get Image shows panel. Everything else is pixel-identical to FP.Get Image (measured).
* **Minimized panel:** LabVIEW ignores input to it. The server restores it with `ShowWindow(SW_SHOWNOACTIVATE)`, without taking focus.

### Start and Stop

`RemoteVI Start.vi` reports a server that cannot serve. One Server Loop per LabVIEW application instance (it is not reentrant): when it is already running, Start launches nothing and returns error 5001. Otherwise it launches the loop and waits until the loop has created its TCP listener - the loop sends the listener's error cluster on the notifier `RemoteVI:<port>:started` - and returns that error (60 when the port is in use; the loop has then already ended), or 5002 when nothing arrives within 2 s. Before this, both cases returned without an error and nothing listened (measured with the previous Start.vi: port held by another process, error out clean).

### HTTP

* `GET /` → `index.html` (embedded constant) with the security headers.
* `GET /ws` with a valid upgrade and same-origin `Origin` → IG `Prepare WebSocket Upgrade Response` → `Write Response to TCP`. From then on, the raw TCP connection carries our WebSocket frames.
* Anything else → `404`. One request per connection.

## Code organisation

```
source/
├── API/        RemoteVI Start.vi, RemoteVI Stop.vi           (what you put in your VI)
├── Server/     Server Loop.vi and its parts (Accept Clients, Track Popups, Service Clients,
│               Capture And Send, Send Overlay, ...), Handle Connection.vi, Index HTML.vi
├── Capture/    RemoteVI Capture Panel.vi, RemoteVI Dirty Rects.vi, RemoteVI Encode Rect PNG.vi
├── Protocol/   RemoteVI Frame Encode.vi, RemoteVI Overlay Encode.vi, RemoteVI Parse Input.vi,
│               RemoteVI WS Encode Server Frame.vi, RemoteVI WS Decode Client Frame.vi
├── Input/      Translate Input.vi, Post Input.vi (allow list, coordinate mapping, popup clicks),
│               Prepare Menu Click.vi, Post Menu Key.vi (submenus driven with VK_LEFT/VK_RIGHT),
│               Track Modifiers.vi, Apply Modifiers.vi (remote modifier keys -> LabVIEW's key state)
└── Win32/      Find Popups.vi, Capture Window.vi, Hide Window.vi, Wait Popups Change.vi, ...
                Mouse Captured.vi, Set Modifier Keys.vi, Wait Input Handled.vi
                user32/gdi32/kernel32 *.vi wrappers   (generated, do not edit by hand;
                GetKeyboardState/SetKeyboardState run in the UI thread, the rest in any thread)
scripts/        Build Win32 Wrappers.vi (+ builder subVIs and templates)
tools/aixml/    AIXML sources of the generated VIs, for regeneration
tools/lib, tools/mock-server   JS reference implementation + reference server
web/index.html  the browser client
examples/       RemoteVI Demo.vi (and the layout helper that arranges its panel)
spikes/         benchmarks (Dirty Rects, PNG levels) and a Start/Stop error check; the original
                measurement spikes are in git history (before the cleanup commit)
```

Every pure VI (Protocol, Dirty Rects) has a JS reference function and shared vectors in `tests/vectors/`.
